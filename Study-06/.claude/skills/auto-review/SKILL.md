# 자동 코드 리뷰

코드를 **읽고 점검만** 한다. 리뷰하는 동안 파일을 고치지 않는다.
고칠 점은 제안으로 남기고, 실제로 고칠지는 사용자가 정한다.
(보고서를 보여준 뒤 사용자가 "고쳐줘"라고 하면 그때 고친다.)

## 1단계: 리뷰할 대상 정하기

1. 사용자가 파일이나 폴더를 지정했으면 그것을 리뷰한다.
2. 지정이 없으면 최근에 바뀐 코드를 찾는다.
   - `git status`와 `git diff`로 아직 커밋하지 않은 변경을 본다.
   - 변경이 없으면 `git log -1 --stat`으로 마지막 커밋에서 바뀐 파일을 본다.
3. 그래도 대상이 없으면 무엇을 리뷰할지 사용자에게 물어본다.
4. 바뀐 줄만 보지 말고, 그 코드를 부르는 곳과 그 코드가 부르는 곳도 함께 읽는다.
   버그는 두 코드가 만나는 곳에서 자주 생긴다.

## 2단계: 규칙 읽기

이 저장소에는 린터(코드 스타일 자동 검사기)나 스타일 설정 파일이 없다. 규칙은 `CLAUDE.md`에 있다.

- 저장소 맨 위 `CLAUDE.md` (공통 규칙)
- 리뷰 대상이 들어 있는 `Study-NN/CLAUDE.md` (그 폴더의 규칙과 구조)
- 그 폴더에 `PRD*.md`가 있으면 요구사항도 확인한다

## 3단계: 점검하기

[checklist.md](checklist.md)의 항목을 순서대로 점검한다.
중요도 순서: **보안 > 버그 > 코딩 규칙·읽기 쉬움 > 성능**.

확인 방법:
- 문법 오류만 빠르게 확인할 수 있다: Python은 `python3 -m py_compile <파일>`, JS 파일은 `node --check <파일>`
- 앱 실행이나 실제 API 호출이 필요한 확인은 하지 않는다. 보고서에 "Colab에서 직접 확인할 것"으로 적는다
- 추측으로 문제를 만들지 않는다. 확실하지 않으면 "확인 필요"라고 따로 표시한다
- 학습용 저장소다. 체감되지 않는 미세한 최적화나 취향 차이는 지적하지 않는다

## 4단계: 보고하기

[report-template.md](report-template.md)의 형식대로 한국어로 보고한다.

- 사용자는 코딩 초보자다. 전문 용어는 쉬운 말로 풀어 쓴다 (예: "예외 처리(오류가 나도 앱이 멈추지 않게 막는 코드)")
- 문제마다 `파일경로:줄번호`와 **어떤 상황에서 문제가 생기는지**를 꼭 적는다
- 심각한 것부터 쓴다. 해당 항목이 없으면 "없음"이라고 쓴다
- 마지막에 "고쳐드릴까요?"처럼 다음 할 일을 한 줄로 묻는다
